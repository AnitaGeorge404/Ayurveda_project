# Data Cleaning & Normalization Decisions

This document records every transformation applied to the raw source data
before it entered Neo4j, per the project requirement that no information be
discarded without documentation. Generated by `scripts/ingest_excel.py`.

## Raw sources

| File | Description |
|---|---|
| `data/raw/Category_Medhya.xlsx` | Original spreadsheet (`Sheet1`, 8 columns × 1177 rows, sparse). Columns A–C are independent controlled vocabularies (not row-aligned to each other). Columns F–H (merged header "Herb–function–pathology relationships") are a curated 9-row table. |
| `data/raw/relationships_medhya.txt` | A Neo4j Cypher query result export (`n,r,m` columns) supplied directly by the domain expert, covering 9 herbs with `HAS_ACTION`, `TREATS_PATHOLOGICAL`, `AFFECTS_PHYSIOLOGICAL`, `HAS_REFERENCE` relationships. Treated as an equally authoritative source, not LLM-generated. |

## Column inventory (`Category_Medhya.xlsx`)

- **Col A `Physiological / Functional`** — 171 term vocabulary (Satva, Rajas, Medha, Smriti, Ojas, …). Loaded as `(:PhysiologicalFunction)` vocabulary nodes.
- **Col B `Pathological`** — 43 term vocabulary (Smritinasa, Apasmara, Unmada, …). Loaded as `(:Pathology)` vocabulary nodes.
- **Col C `Pharmacotherapeutics`** — 41 entries. **Mixed content**, split as follows (see `data/canonical_entities.json`):
  - Real herb names + spelling variants + botanical/English synonyms → merged into 10 canonical `(:Herb)` entities via a manually curated alias map (e.g. `Shankhapushpi` / `Shankhpushpi` / `Sankhpushpi` → one node; `Bacopa` / `Jalabrahmi` → `Brahmi`; `Gotu kola` / `Thankuni` → `Mandukaparni`).
  - `Medhya Rasayana`, `Rasayana`, `Vanausadhi` are **classifications, not individual herbs** — kept as a distinct `(:Category)` label rather than merged into `(:Herb)`, so a query for "herbs" never silently returns a category.
  - `Dravya`, `Guna`, `Virya`, `Vipaka`, `Prabhava` are the five classical Ayurvedic pharmacology parameters, not herbs or synonyms of herbs — labeled `(:PharmacologicalConcept)`. No relationship data exists for these; they are intentionally kept as vocabulary-only nodes so a question about them correctly triggers `INSUFFICIENT_EVIDENCE` rather than `OUT_OF_DOMAIN` (the term is real, evidence isn't).
  - `Ayushya`, `Balya`, `Ojovardhana`, `Jeevaniya`, `Vayasthapana`, `Pushtikara` are physiological/functional effect terms that appear to have been miscategorized into the Pharmacotherapeutics column (they duplicate concepts already present in Column A, and appear as `physiologicalFunctional` values for Ashwagandha/Guduchi in the second source). Reclassified as `(:PhysiologicalFunction)`, not `(:Herb)`.
- **Cols F–H** (`Herb–function–pathology relationships`) — a 9-row curated table: `Pharmacotherapeutics → Physiological/Functional(s) → Pathological(s)`, with the latter two columns comma-packing multiple values per cell. Each comma-separated value was split into its own edge, each carrying the full original row text as `source_text` for auditability. Two of the 9 rows (`Medhya Rasayana`, `Rasayana`) are category-level, not herb-level, per the split above.
  - One pathology value, `cognitive disturbance` (row 5, Guduchi), does not match the 43-term controlled Pathological vocabulary in Column B. It was **not discarded** — it is loaded as a `(:Pathology)` node like any other, simply without a matching controlled-vocabulary entry elsewhere.

## `relationships_medhya.txt` parsing

Each line has the form:
```
(:Pharmacotherapeutic {pharmacotherapeutics: Brahmi}),[:HAS_ACTION],(:Action {action: Smritiprada})
```
Parsed with a regex into `(subject_label, subject_value, relationship, object_label, object_value)`. The subject value is run through the same alias map as above (so `Mandukaparni` here resolves to the same canonical `(:Herb)` node as the spreadsheet's `Mandukaparni`/`Mandukparni`/`Gotu kola`/`Thankuni`). Relationship names are normalized: `TREATS_PATHOLOGICAL → TREATS_PATHOLOGY`, `AFFECTS_PHYSIOLOGICAL → AFFECTS_FUNCTION` (kept consistent with the naming used for the spreadsheet-derived edges of the same meaning); `HAS_ACTION` and `HAS_REFERENCE` are kept as-is.

Any line that fails to match the expected pattern is **not silently dropped** — it is recorded as an `(:UnparsedLine)` node carrying the line number, so a human can review `data/processed/nodes.csv` and recover it. (In the current data, 0 lines failed to parse.)

## Known ambiguity, kept as-is (not resolved)

`Rasayana` and `Medhya` each appear twice with different roles: once as a `(:Category)` name (`Rasayana` as a class of herbs) and once as a `(:PhysiologicalFunction)` value (`Rasayana`/`Medhya` describing a rejuvenative/nootropic *effect* a herb has, e.g. "Brahmi AFFECTS_FUNCTION Rasayana"). These do not collide in the graph because they are different node labels, but a question mentioning "Rasayana" is ambiguous between the two senses. The question analyzer resolves this by preferring the entity type implied by the requested relationship (e.g. "what does Rasayana treat" → Category; "what herbs have Rasayana effect" → PhysiologicalFunction).

## Provenance

Every node retains: `source_files` (which raw file(s) it was seen in), `source_rows` (spreadsheet row numbers / text file line numbers). Every edge retains `source_file`, `source_row`, and `source_text` (the original row/line verbatim), so any answer can be traced back to an exact row in the original data. This is loaded into Neo4j as relationship properties by `scripts/load_neo4j.py`.
